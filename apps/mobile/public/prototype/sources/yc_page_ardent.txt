**How did we get here (the problem)?**

Ardent was a reaction to the failure of our last product - an AI Data Engineer. It was a coding agent that generated data pipelines, wrote migrations, backfills and other things you’d expect of a data engineer.

While the code _looked_ great we had no way of testing generated code. Writing to prod was out of the question and dev environments were never in sync, shared amongst devs which caused write clashes between agents, and was a huge pain to manage. **_What we needed was a ephemeral DB sandbox per agent of the user’s DB._**

Because of how hard testing was, generated code would never be tested and was too unstable to put in production. Database failures almost always mean downtime, a risk both we and customers were obviously not willing to take. We churned almost 200K in ARR

This problem exists with any coding agent today. We’re shipping 100x more DB code to production and we mostly just hope to god it works the same as dev.

**Ardent - Isolated &lt;6s database clones that let you test agent code:**

Ardent solves the DB sandbox problem by letting you create 6s clones of ANY postgres DB regardless of size, allowing you to give every developer and every agent a full copy of production or dev to test against.

Clones autoscale to zero when not in use, use copy on write for massive storage efficiency and can be loaded with a single CLI command (zero infra management)

You can see the exact results of any code run against the DB in a perfect 1:1 reproduction and don’t have to change your DB provider.

The entire thing runs as a CLI that feels exactly like git. Cloning is as simple as “ardent branch create &lt;name&gt;”

This means you can spin up instant environments to test _every_ line of DB code with none of the overhead

**Asks**

**Use Ardent at your company to go faster by let agents work safely at the DB layer and prevent regressions:** <https://cal.com/vikram-chennai/yc-reserved>

**Introduce me to series A-C engineering leaders (Founders, CTOs, VP of Eng):** Many of the later stage startups we’ve talked to have the majority of their engineers shipping with claude, codex or cursor on migrations, backfills and pretty much any code that hits the DB. They will eventually crash their production DB unless they’re rigorously testing. I’d like to prevent those crashes :)
