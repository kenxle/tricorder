# User stories

## Charter

**What belongs:** The user stories behind Tricorder's features, each in the form "when I ..., I want ..., so I ...", with who it is for and the feature or roadmap slice that serves it.

**What does not:** The high-level jobs to be done (they live in [PRODUCT_BRIEF.md](PRODUCT_BRIEF.md), "The jobs to be done"). How a feature is built ([ARCHITECTURE.md](ARCHITECTURE.md), [ROADMAP.md](ROADMAP.md)).

**Level of detail:** One line per story, plus who and where it is built.

**Sources:** moved from the product brief on 2026-10-22 at Ken's comment ("these are user stories, which belong in feature documentation"); [PERSONAS.md](PERSONAS.md); [ROADMAP.md](ROADMAP.md).

## The associate who prepares the memo

- When a deck lands in my inbox, I want the first pass done before I open it, so I can decide in minutes whether to take the meeting.
- When I open a readout, I want the best green flags and the worst red flags first, then an overview of which pieces of the company look strong and which look weak, with the disagreements one click down, so I know what to ask in the second meeting.
- When a startup reports ARR, I want it rebuilt from the contracts and the revenue rows, so I know how much of it is truly recurring.
- When a fact is missing from the room, I want to see it marked as missing and put on a list of what to ask the founder for, so I ask for it instead of trusting a guess.
- When I compare the startup with others, I want comparable companies and rounds with the reason each one is fair.
- When I watch the pitch video, I want to jump to each claim and see which ones disagree with the deck.
- When I write the memo for the partners' meeting, I want every claim tied to its source, so I can defend it to people who never met the founder.
- When a piece of the readout looks wrong or thin, I want to say so in one sentence and get it rewritten or filled in, with no setup.

## The partner who reads the memo

- When I read a memo on a deal I did not work, I want to drill from any line to its sources and try my own what-ifs on the model, so I can trust it without redoing the work.
- When I disagree with an assumption in the growth model, I want to change it myself and see what the numbers become, marked as my scenario.

## Secondary personas

- When I write a small check alone, I want a first pass whose cost fits the check.
